## 1. Critical

### `EVENT-001` — Real-time online/offline tracking has never run

**Location:** [Modules/Events.lua:415](../Modules/Events.lua#L415)

```lua
function TOGBankClassic_Events:CHAT_MSG_SYSTEM(message)
```

Every other handler in the file absorbs the event name in a leading `_`
(`PLAYER_ENTERING_WORLD(_, isInitialLogin, isReloadingUi)`, `UI_ERROR_MESSAGE(_, message)`).
This one does not, so `message` receives the literal string `"CHAT_MSG_SYSTEM"` and the real
chat text is dropped. Every `:match` in the body fails and the function always returns having
done nothing.

**Verified, not assumed** — against the installed Ace3:

- `Ace3/AceEvent-3.0/AceEvent-3.0.lua:120` — `events:Fire(event, ...)`
- `Ace3/CallbackHandler-1.0/CallbackHandler-1.0.lua:54` — `Dispatch(events[eventname], eventname, ...)`
- AceEvent-3.0 doc header, line 58: *"the event name as the second (or first, if no arg was
  supplied). Any arguments to the event will be passed on after that."*

**Dead as a result:** player-came-online detection; player-went-offline detection; the
`"No player named X is currently playing"` offline marking (which the code itself labels
`CRITICAL` and *"the AUTHORITATIVE offline signal"*, existing to prevent whisper spam); and the
`has joined/left the guild` roster-refresh trigger.

**Knock-on:** the comment above the handler calls this *"PRIMARY method for tracking
online/offline state changes in real-time."* Because it never runs, `onlineMembers` only ever
updates on a full `GUILD_ROSTER_UPDATE` refresh. Every consumer degrades:
`Core:SendWhisper`'s online gate, `Guild:RequestHashListFromBanker`'s banker search,
`Guild:QueryAltPullBased`'s banker selection.

**Fix:** add the leading `_` parameter. One character. Add a spec that asserts the handler
receives the message and not the event name.

- [ ] `EVENT-001`

### `ITEM-005` — A single bad item permanently wedges the inventory list

**Location:** [Modules/Item.lua:351-399](../Modules/Item.lua#L351)

`pendingAsync` is incremented before `pcall(Item.CreateFromItemID, Item, capturedItemID)`, but
**seven** failure branches increment `processed` and call `checkComplete()` without ever
decrementing `pendingAsync`:

| Trace | Condition |
| --- | --- |
| TRACE-3 | `not success` (pcall failed) |
| TRACE-4 | `not itemData` |
| TRACE-5 | `type(itemData) ~= "table"` |
| TRACE-8 | `not accessSuccess` |
| TRACE-9 | `objectItemID == nil` |
| TRACE-10 | `type(objectItemID) ~= "number"` |
| TRACE-11 | `objectItemID ~= capturedItemID` |

`checkComplete` requires `processed >= total and pendingAsync == 0`. Once any one of these
fires, `pendingAsync` is stuck above zero and the callback **never** fires — for the entire
batch, not just the offending item. The Inventory window sits on "Loading items…" forever.

Not theoretical: the code's own TRACE-9 message reads
`"FOUND CORRUPTION: itemData.itemID is nil for requested ID %d - THIS IS THE BUG!"`, which
means that branch was observed firing during development.

Separately, there is **no timeout** on `ContinueOnItemLoad`: an item the server never resolves
leaves `pendingAsync` permanently above zero with the same result.

**Fix:** decrement `pendingAsync` on every one of the seven paths (or restructure so the
counter is owned by a single release helper). Add a watchdog for the never-resolves case. Spec
this with an env stub whose `Item.CreateFromItemID` returns nil for one ID in a batch and
assert the callback still fires with the remaining items.

- [ ] `ITEM-005`

## 2. High

### `TIMER-001` — `C_Timer.After` is treated as cancellable in eight places

`C_Timer.After(seconds, callback)` returns **nothing**. Only `C_Timer.NewTimer` and
`C_Timer.NewTicker` return a handle with `:Cancel()`. Every site below stores the `After`
result and later calls `:Cancel()` on it. None of them error, because each cancel sits behind
an `if timer then` guard that is always false — so they fail **silently**.

| Site | Effect |
| --- | --- |
| [P2PSession.lua:121-124](../Modules/P2PSession.lua#L121) | **Harmful.** Re-entering `BeginCollectWindow` while collecting stacks a *second* 60s timer instead of replacing the first. Each fires `P2P:Dispatch()`, and `Dispatch` never clears `self.offers`, so the same alts get dispatched repeatedly. |
| [P2PSession.lua:323](../Modules/P2PSession.lua#L323), [:362](../Modules/P2PSession.lua#L362) | Benign — the stale timer's `state == STATE.DISPATCHED` guard absorbs it. |
| [P2PSession.lua:335](../Modules/P2PSession.lua#L335), [:384](../Modules/P2PSession.lua#L384) | Benign — same, via `sessions[sessionId]` being nil after completion. |
| [P2PSession.lua:461](../Modules/P2PSession.lua#L461) | `CancelTimers` is wholly a no-op (`type(timer) == "table"` fails on nil). |
| [Chat.lua:784](../Modules/Chat.lua#L784), [:848](../Modules/Chat.lua#L848) | The 5s and 15s P2P fallbacks can never be cancelled — see `DOC-001`. |
| [Guild.lua:1183](../Modules/Guild.lua#L1183) | `pendingP2PTimeouts` never holds a real handle. |

**Telling detail:** [P2PSession.lua:99](../Modules/P2PSession.lua#L99) reads
`self.catchUpTimer = true -- set before C_Timer.After in case it returns nil`. The knowledge
existed in exactly one place and was not applied to the other eight.

**Fix:** switch every cancellable site to `C_Timer.NewTimer`. Leave fire-and-forget `After`
calls alone. The collect-window site is the one that changes behaviour; the rest are
correctness/clarity.

- [ ] `TIMER-001`

### `P2P-024` — Send-slot cap can be exceeded by delayed safety releases

**Location:** [Modules/P2PSession.lua:492](../Modules/P2PSession.lua#L492)

`TryAcquireSendSlot` unconditionally schedules a `SEND_TIMEOUT` (210s) `ReleaseSendSlot`. When
a send finishes normally, `ReleaseSendSlot` runs at completion **and** the safety timer still
fires later — decrementing a slot that by then belongs to a **different, later** send from the
same requester. The `> 0` guard prevents underflow but not over-release, so
`MAX_ACTIVE_SENDS = 3` can be quietly exceeded under sustained load.

**Fix:** make the safety release idempotent per acquisition (token/generation counter, or a
cancellable `NewTimer` cancelled by the real release).

- [ ] `P2P-024`

### `MIGRATE-001` — Legacy hash migration calls `ComputeInventoryHash` with the wrong arity

**Location:** [Modules/Database.lua:341](../Modules/Database.lua#L341)

```lua
alt.inventoryHash = TOGBankClassic_Core:ComputeInventoryHash(alt.bank, alt.bags, money)
```

The signature is `ComputeInventoryHash(bank, bags, mail, money)`. `money` lands in the `mail`
slot and the `money` parameter is nil. Every pre-v0.8 saved character is migrated to a **bogus
`inventoryHash`**, which then drives all downstream hash-comparison sync decisions
(`IsAltSyncPending`, `BuildBankerHashList`, `RespondToStateSummary`).

The next line formats the result with `%08x`, which raises if the call returns a non-number.

Note the call also passes `alt.bank`/`alt.bags` (the container tables), whereas `Bank:Scan`
passes `alt.items` (the aggregated array) — see `SYNC-006` in the changelog. The two produce
different hashes for the same character, so this migration cannot agree with a live scan even
after the arity is fixed. Both need reconciling together.

- [ ] `MIGRATE-001`

### `P2P-025` — The P2P send-queue backpressure is dead scaffolding

**Locations:** `Modules/Guild.lua` (declaration line 32-34, uses at 2021, 2079, 2517, 2542-2564)

`pendingSendCount` is initialised to `0` and **only ever decremented** — nothing in the current
codebase increments it. `pendingSendTimeouts[norm]` is **only ever assigned nil** — never given
a timer. Consequences:

- `MAX_PENDING_SENDS = 3` throttles nothing. The cap does not exist.
- [Guild.lua:2542](../Modules/Guild.lua#L2542) `local isP2PSend = self.pendingSendTimeouts and self.pendingSendTimeouts[norm] ~= nil`
  is permanently `false`, so `releaseP2PSlot` is a no-op on every early-return path it was
  written to protect.
- [UI/StatusBar.lua:175](../Modules/UI/StatusBar.lua#L175) reports a queue depth that is always 0
  — a diagnostic that lies.

`docs/DELTA_BUGS.md:4365` describes the increment at "Chat.lua line 825". The refactor to
`P2PSession.activeSends` removed it and left the husk behind, still reading as live logic.

**Fix:** delete the dead machinery (`pendingSendCount`, `pendingSendTimeouts`, `isP2PSend`,
`releaseP2PSlot`, `MAX_PENDING_SENDS`) and point the StatusBar at `P2PSession.activeSends`,
which is the mechanism that actually runs. Update `docs/DELTA_BUGS.md` so it stops describing
removed code as current.

- [ ] `P2P-025`

## 3. Medium

### `DEBUG-001` — Three debug calls emit garbled text

An unrecognised tag is silently treated as the format string, shifting every argument. Output
becomes e.g. `MIGRATION [GHOST-PURGE] Removed linkless gear ID=%d from %s.%s 12345 Bob items`
— raw `%d` in the message and the real format string printed as data.

| Site | Problem |
| --- | --- |
| [Output.lua:83](../Modules/Output.lua#L83), [:442](../Modules/Output.lua#L442), [:459](../Modules/Output.lua#L459) | `"SYSTEM"` is not a `DEBUG_CATEGORY` at all |
| [RequestLog.lua:2070](../Modules/RequestLog.lua#L2070), [:2075](../Modules/RequestLog.lua#L2075), [:2077](../Modules/RequestLog.lua#L2077), [:2153](../Modules/RequestLog.lua#L2153), [:2158](../Modules/RequestLog.lua#L2158) | `"FULFILL"` is not a `DEBUG_CATEGORY` at all |
| [Database.lua:79](../Modules/Database.lua#L79) | `"MIGRATION"` — the tag is `MIGRATE` |
| [Chat.lua:212](../Modules/Chat.lua#L212) | `"HASH-ADOPT"` — not in `DEBUG_TAGS.SYNC` |

**The five `FULFILL` sites were found by the test suite, not by the manual read** —
`RequestLog.lua` is one of the modules listed as unread in §0. The scan in
`Tests/constants_spec.lua` covers all files, which is why it caught them. Everything else in
the tree is valid.

**Fix:** add `SYSTEM` and `FULFILL` as real categories (three-way: `DEBUG_CATEGORY`,
`Database:Init` defaults, `CATEGORY_META`) or retag those calls to existing ones; correct
`MIGRATION`→`MIGRATE`; register `HASH-ADOPT` in `DEBUG_TAGS.SYNC`. The regression guard is
already in place — `constants_spec.lua` walks every `Debug()` call site in every file, so this
class cannot silently return.

- [ ] `DEBUG-001`

### `LOG-001` — Log garbage collection writes into the log it is collecting

**Location:** [Output.lua:442](../Modules/Output.lua#L442) via [:328](../Modules/Output.lua#L328)

`GarbageCollectPersistentLog` finishes with a `Debug()` call, and `Log()` appends every
DEBUG-level message to the persistent log. So each collection pass adds an entry to the log it
just collected: the log can never drain to empty, and every pass seeds the next one.

Harmless at current volumes and recorded here rather than asserted as a defect — but it should
be a deliberate choice, not an accident. Pinned as *behaviour* by
`Tests/output_spec.lua › writes its own summary back into the persistent log`, so a future
change to it is visible rather than silent.

- [ ] `LOG-001`

### `ITEM-006` — `IsUnique` leaks a named frame on every call

**Location:** [Modules/Item.lua:732](../Modules/Item.lua#L732)

```lua
local tip = CreateFrame("GameTooltip", "scanTip", UIParent, "GameTooltipTemplate")
```

Called per invocation. WoW frames cannot be destroyed, so each call leaks one and clobbers the
global `scanTip`. Also `l:find(ITEM_UNIQUE)` treats a localised string as a Lua pattern; it
should be a plain find (`, 1, true`).

**Fix:** create the scanning tooltip once, module-scope, and reuse.

- [ ] `ITEM-006`

### `NS-001` — Global namespace pollution

`Modules/Constants.lua` declares **eleven bare globals**: `ADOPTION_STATUS`,
`TIMER_INTERVALS`, `LOG_LEVEL`, `DEBUG_CATEGORY`, `DEBUG_TAGS`, `REQUEST_LOG`,
`REQUESTS_SYNC`, `COMM_PREFIX_DESCRIPTIONS`, `PROTOCOL`, `PEER_TO_PEER`, `FEATURES`.
`PROTOCOL` and `FEATURES` in particular are collision magnets with other addons — and a
collision here silently changes sync behaviour rather than erroring.

Also:

- [Guild.lua:110](../Modules/Guild.lua#L110) — `function GetPlayerWithNormalizedRealm(name)`,
  a bare global function with a very generic name.
- [Database.lua:105](../Modules/Database.lua#L105) — `_ = guildName` writes a global `_` on
  every loop iteration.

**Fix:** move the constants under `TOGBankClassic_Constants` (or prefix each), per the module
namespace rule in `CLAUDE.md`. This touches many call sites, so it is best done as its own
commit with the test suite already green.

- [ ] `NS-001`

### `HIGHLIGHT-001` — Bank bags dim the wrong slots

`UpdateDefaultBagHighlighting` reverses slot order
([ItemHighlight.lua:603](../Modules/ItemHighlight.lua#L603)) because WoW's button numbering
runs opposite to API slot numbering:

```lua
local buttonSlot = numSlots - apiSlot + 1
```

`UpdateBankHighlighting` calls `GetBagSlotButton(bag, slot)` for bags 5-11
([:646](../Modules/ItemHighlight.lua#L646)) with **no reversal**. The two cannot both be
correct — bank-bag highlighting is mirrored relative to bag highlighting.

- [ ] `HIGHLIGHT-001`

### `HIGHLIGHT-002` — Crash risk on unnamed buttons; un-clearable overlays

**Location:** [ItemHighlight.lua:227](../Modules/ItemHighlight.lua#L227), [:250](../Modules/ItemHighlight.lua#L250)

```lua
local icon = button.icon or button.Icon or _G[button:GetName().."IconTexture"]
```

Lua evaluates the concat even as the third `or` operand, so an anonymous frame
(`GetName()` → nil) raises *"attempt to concatenate a nil value"*. Third-party bag addons use
anonymous buttons routinely.

`ClearAllOverlays` keys overlays by `tostring(button)` for unnamed buttons, then tries to
resolve them back via `_G[buttonKey]` — which cannot work — and skips them. Those overlays are
never cleared.

- [ ] `HIGHLIGHT-002`

### `HIGHLIGHT-003` — Dead write outside the AceDB scopes

**Location:** [ItemHighlight.lua:121-124](../Modules/ItemHighlight.lua#L121)

```lua
TOGBankClassicDB.settings.highlightEnabled = enabled
```

Writes to the raw AceDB root table — neither `db.global` nor `db.faction[guild]`, contrary to
the AceDB scoping rule in `CLAUDE.md`. Nothing ever reads it: `Initialize` hardcodes
`self.enabled = false` with the comment *"Don't auto-enable from saved settings"*.

**Decide:** either honour the saved setting (and move it to a proper scope) or drop the write.

- [ ] `HIGHLIGHT-003`

### `BANK-002` — `TOGBankClassic_Bank` is constructed from the chunk varargs

**Location:** [Modules/Bank.lua:2](../Modules/Bank.lua#L2)

```lua
TOGBankClassic_Bank = { ... }
```

At file scope `...` is the addon vararg the client passes in, so the table is born containing
`[1] = "TOGBankClassic"`, `[2] = <addon namespace table>`, and `#TOGBankClassic_Bank == 2`.
Almost certainly meant to be `{}`. Harmless today; a trap for any future `ipairs`/`#` over the
module table.

- [ ] `BANK-002`

### `DOC-001` — Comments assert behaviour the code does not have

`CLAUDE.md` forbids aspirational comments explicitly. These are load-bearing and misleading:

- [Events.lua:270](../Modules/Events.lua#L270) — *"Clear flag once the final chunk is confirmed
  sent by CTL."* AceComm invokes the callback for **every** chunk and the code ignores the
  `sent`/`total` arguments, so the flag clears on the **first** chunk. The `P2P-023` collision
  guard is far weaker than the comment claims.
- *"Store timeout timer for cancellation if peer responds"* (three sites) — nothing cancellable
  is stored. See `TIMER-001`.
- `docs/DELTA_BUGS.md:740-741` marks `P2P-012` and `P2P-013` ✅ **fixed**. Both fixes are inert
  because of `TIMER-001`; `P2P-013`'s stated symptom (duplicate banker fallback from two
  concurrent timeouts) is still live.

Fix the comments together with the code they describe, and correct the ✅ marks in
`DELTA_BUGS.md`.

- [ ] `DOC-001`

### `PERF-022` — Tooltip hover is O(bankers × items)

**Location:** [Modules/TooltipBankerInfo.lua:26](../Modules/TooltipBankerInfo.lua#L26)

Every item mouseover walks every alt's entire item array. Ten bankers × 1,000 items ≈ 10,000
iterations per hover, on one of the hottest paths in the game client.

**Fix:** maintain an `itemID → {banker, count}` index, rebuilt when alt data changes rather
than per hover.

- [ ] `PERF-022`

### `LINT-001` — `Options.lua` carries a UTF-8 BOM

The only file in the tree that does, and the only one `luac -p` rejects
(`unexpected symbol near '<bom>'`). Stripping the BOM makes it parse clean; there is no other
syntax problem in the file. WoW tolerates a BOM, so this is not a live bug — but it blocks
`luac`, `luacheck`, and the offline test harness on that file specifically, which matters now
that the suite exists.
